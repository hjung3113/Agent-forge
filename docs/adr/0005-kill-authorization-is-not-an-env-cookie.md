# Process-kill authorization uses the strongest Phase-0-verified OS identity, not an environment-variable cookie

Recovering from a crashed Controller instance requires a replacement instance to safely decide whether a still-alive process belongs to the Attempt it's reconciling, so it can either adopt or kill it. The cheap approach — inject a unique `execution_id` into the child process's environment and match on that — was initially proposed as the kill-authorization mechanism. We rejected using it as more than correlation metadata: an environment variable is copyable or strippable by same-UID code, isn't guaranteed to be inspectable on every supported host, isn't guaranteed to survive every descendant process, and doesn't prove every member of a process group actually belongs to the Attempt. Trusting it as authorization would mean a confused or adversarial Worker could potentially cause the wrong process to be killed, or a legitimate process to escape cleanup undetected. Instead, kill authorization requires the strongest OS-level process identity and containment mechanism the Phase 0 capability survey actually proves is available on the target platform (process-group with corroborating start-time, cgroup, job object, or similar); the cookie remains useful correlation data but never the sole basis for signaling a process. When identity is ambiguous, the rule is fail-closed: do not signal, mark the Attempt `LOST`, preserve the lease for operator intervention, rather than risk killing or adopting the wrong process. This means recovery correctness is gated on what Phase 0 can actually measure per host, not on an assumption that always holds.
